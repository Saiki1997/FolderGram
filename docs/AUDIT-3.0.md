# FolderGram 2.3.0 audit and 3.0 plan

Audited commit `4970068` (v2.3.0). All 16 existing tests pass. Severity: **Critical** can lose data or post
duplicates, **High** breaks uploads or freezes the app at scale, **Medium** is wrong or wasteful, **Low** is hardening.

## Findings

| # | Severity | Where | Problem | Fix in 3.0 |
|---|---|---|---|---|
| 1 | Critical | `uploader.js` `UploadHistory` constructor | A corrupt or half-written `uploaded.json` is silently replaced by `{}`, and the next save overwrites it. All upload history is lost and everything is re-sent. | New `store.js`: atomic write with fsync, `.bak` copy, automatic recovery from the backup, corrupt file kept aside, daily backups. |
| 2 | Critical | `uploader.js` `withRetry` + `telegram.js` `sendAlbum` | When the connection drops after Telegram received an album but before the reply arrives, the retry sends the whole album again (a duplicate post). A new random message id is generated on every attempt, so Telegram can't de-duplicate. | Each album gets stable `random_id`s that are reused on every retry and after a restart. Telegram answers `RANDOM_ID_DUPLICATE` instead of posting twice; that is treated as delivered. Uncertain sends are checked against the topic's recent messages before resending. |
| 3 | Critical | `scanner.js` `renamer` | "Album 1, Album 2…" numbers depend on folder order. Adding a source or a new folder renumbers them, the topic name changes, the resume key changes, and already-sent files go again into a different topic. | Random-name stand-ins are remembered per name (`naming.json`), so the same folder always gets the same number. |
| 4 | High | `main.js` window `close` | Quitting during an upload calls `cancel()` and exits; history is only written every 5 s and in `finally`, which may not run. Up to 5 s of sent albums are forgotten and re-sent. | History is appended to a journal after each album (durable immediately) and flushed synchronously on quit. Job state is persisted, so the job can be resumed. |
| 5 | High | `uploader.js` `topicFor` | `createTopic` has no retry; a timeout aborts the whole job. If the topic was created but the reply was lost, a rerun creates a second topic with the same name. | Topic creation goes through the retry policy, and the topic list is re-read before creating again. |
| 6 | High | `uploader.js` `fingerprint` | Duplicate check uses synchronous `fs.openSync/readSync` on the Electron main process for every file before the upload starts (151 ms for 10,000 small files on SSD here; on a hard disk or network share this freezes the window for minutes). | Async fingerprints, done in a worker thread for full hashes, with bounded concurrency and progress. |
| 7 | High | `uploader.js` duplicate detection | Fingerprint is size + first/last 64 KB. Files that differ only in the middle (WAV/BMP/TIFF, re-muxed video with identical header/trailer) are wrongly skipped. No way to review what was skipped. | Quick fingerprint now also samples the middle; any quick match is confirmed with a streamed SHA-256 when both files are available; unverifiable matches are marked "probable" and shown in a review list before upload. Hashes are cached by path + size + mtime. |
| 8 | High | `scanner.js` `fileStem('loose')` | `Episode 01`, `Season 2`, `Set 01`, `Part 1` lose their number and merge into one album named "Episode"/"Set". `Resident Evil 4` becomes "Resident Evil". | New naming engine separates content identifiers (Episode/Set/Volume/Part/Chapter/SxxEyy) from sequence numbers, and treats a trailing number as a sequence only when sibling files form a series. |
| 9 | High | `scanner.js` `isGibberish` | Misses UUIDs, long hashes, names with `_`/`-`, names over 16 chars, camera/timestamp names. False positives on real acronyms (`PSVR`, `BTS`-style all-caps names without vowels). | Multi-signal randomness score (entropy, case changes, digit/letter switches, vowel ratio, dictionary-like syllables, hex/UUID/base64 shapes) with a confidence value; low-confidence names are kept and flagged in the preview. |
| 10 | Medium | `uploader.js` `withRetry` | Retries every error the same way (4 tries, 3/6/9 s, no jitter), including permanent ones (`CHAT_WRITE_FORBIDDEN`, `TOPIC_CLOSED`, `MEDIA_CAPTION_TOO_LONG`). Flood waits and pauses are plain `setTimeout`s, so Cancel waits until a FloodWait (can be minutes) ends. | Error classification (flood / network / temporary file / permanent / already delivered), exponential backoff with full jitter, configurable retries, cancellable waits with a visible countdown. |
| 11 | Medium | `telegram.js` login | `floodSleepThreshold: 120` makes GramJS sleep silently for flood waits up to 2 min inside `invoke`, invisible to the UI and impossible to cancel. | Threshold lowered to 5 s so FolderGram handles waits itself. |
| 12 | Medium | `uploader.js` `sendWithSplits`, `telegram.js` mixed albums | An album that becomes several messages (split video parts, or photos + files) is retried as a whole: parts already posted are posted again. | Each message of an album has its own stable ids and status, so a retry continues with the next part. |
| 13 | Medium | `uploader.js` retries | Every retry uploads all files of the album again (up to 20 GB for 10 × 2 GB videos). | Uploaded media are cached for the session; a retry only re-sends the message. |
| 14 | Medium | `uploader.js` cancel | Cancel only takes effect after the current album finishes uploading. | Uses GramJS' `onProgress.isCanceled` to stop the running file upload. |
| 15 | Medium | `telegram.js` captions | Captions over 1,024 characters fail permanently (`MEDIA_CAPTION_TOO_LONG`) after 4 retries. | Captions are cleaned of control characters and safely shortened. |
| 16 | Medium | `uploader.js` topic matching | Two existing topics with the same name: the last one wins silently. Closed topics are reused and every send fails. | Topics are matched on a normalised name; duplicates and closed topics are shown as warnings in the preview and can be mapped manually. |
| 17 | Medium | `renderer/app.js` | Every option change (caption placement, topic source, name rules) rescans the disk. | Scan results are cached in the main process; caption and naming changes only re-plan. |
| 18 | Medium | `main.js` `upload:start` | The upload rescans and rebuilds the plan, so what is sent can differ from what was previewed, and no manual changes are possible. | The upload uses the previewed (and edited) plan; files changed since the scan are detected and reported. |
| 19 | Medium | `renderer/app.js` `renderPlan` | The whole plan is rendered as one HTML string; 1,000 folders means thousands of cards and full-size image decodes for thumbnails. | Virtualised list (only visible rows are in the DOM), small cached thumbnails from the Windows thumbnail cache. |
| 20 | Medium | `uploader.js` `save` | History is one JSON object rewritten in full (2.8 MB / 135 ms for 50,000 entries here) every 5 s on the main thread. | Append-only journal plus occasional compaction; lookups stay in memory. |
| 21 | Medium | `main.js` `saveSettings` | Not atomic; a crash mid-write leaves invalid JSON, after which all settings (including encrypted API hash) are dropped and overwritten. Same for `session-*.dat`. | Same atomic store with backup and recovery. |
| 22 | Low | `main.js` IPC | No validation of IPC arguments (`sources:scan` accepts anything, `settings:set` accepts any keys). | Typed validation for every handler. |
| 23 | Low | `main.js` window | No `will-navigate` guard; `sandbox` relies on the default. | Navigation blocked, `sandbox: true` explicit. Context isolation on, node integration off (unchanged). |
| 24 | Low | `scanner.js` walk | Symlinks are skipped (good) but there is no depth limit and no visited-folder guard for junction loops on network drives. | Real-path visited set and configurable depth limit. |
| 25 | Low | `splitter.js` | Generated parts aren't checked; an empty or unreadable part fails only at upload time. | Each part's length is read back with ffmpeg before sending. |

What is already good and kept: context isolation, encrypted secrets with `safeStorage`, GramJS MTProto uploads (2/4 GB), photo resizing into albums, lossless video splitting, deterministic natural ordering, throttled progress events.

**SQLite**: evaluated and not adopted. `better-sqlite3` is a native module that must be rebuilt for Electron on Windows, which breaks the current cross-platform portable build (`npmRebuild: false`), and Node's built-in `node:sqlite` is still experimental. The history workload is key lookups plus appends, which an in-memory index with an append-only journal handles with atomic, crash-safe writes and no new dependency. The old `uploaded.json` format is kept, so 2.x can still read it.

## Implementation order

1. **Naming and grouping**: naming engine, random-name detection, hierarchy, confidence, grouping, tests.
2. **Preview**: editable album and topic names, reorder, move/merge/split/exclude, undo/redo, saved plans.
3. **Reliability**: stable message ids and reconciliation, persistent queue with scheduling and resume, duplicate detection, retry policy, crash-safe storage.
4. **Performance**: bounded parallel scanning with progress, scan cache, worker hashing, adaptive concurrency, virtualised preview, thumbnail cache.
5. **Extras**: topic management, live statistics, integrity checks, filters, JSON/CSV reports.
